# 냉털 레시피 서비스 기획서

Oct 8, 2026 · @민선

## 1. 서비스 개요

**한 줄 정의**: 내 냉장고를 화면 속 냉장고로 옮겨 두고, 유통기한이 급한 재료부터 다 먹을 수 있도록 며칠치 식단과 최소 장보기를 짜 주는 모바일 퍼스트 웹 서비스. 홈 화면에 설치해 앱처럼 쓰는 PWA로 제공한다.

**해결하려는 문제**

- 재료를 사 놓고 잊어버려서 유통기한이 지난 뒤에야 발견한다.
- 냉장·냉동·실온 중 어디에 두느냐에 따라 기한이 달라지는데 매번 찾아보기 귀찮다.
- "오늘 뭐 먹지"만 고민하다 보니, 이틀 뒤 상할 재료는 결국 버리게 된다.
- 재료가 애매하게 남았을 때 무엇을 더 사야 요리가 되는지 모른다.

**타깃 사용자**

- 1차: 자취하는 20\~30대 1인 가구. 장보기 단위가 커서 재료가 남기 쉽고, 요리 레퍼토리가 적다.
- 2차: 2\~4인 가구에서 장보기와 요리를 맡은 사람. 냉장고를 가족과 함께 쓴다.

**핵심 가치**

1. 등록이 쉽다: 이름만 넣으면 보관 방식별 유통기한이 자동으로 정해진다.
2. 보면 바로 안다: 실제 냉장고처럼 문을 열면 칸마다 재료가 놓여 있고, 상해 가는 재료가 눈에 띈다.
3. 버리지 않게 된다: 오늘 한 끼가 아니라 앞으로 며칠 동안 무엇을 어떤 순서로 먹을지 알려 준다.
4. 덜 산다: 요리가 막히면 가장 적게 사서 가장 많이 살리는 재료를 추천한다.

**성공 지표 (출시 후 3개월 기준 목표)**

| 지표 | 정의 | 목표 |
| --- | --- | --- |
| 재료 소진율 | 등록 재료 중 '다 씀'으로 끝난 비율 | 80% 이상 |
| 주간 활성 사용자 비율 | 가입자 중 주 1회 이상 앱을 연 비율 | 40% 이상 |
| 플랜 실행률 | 추천된 오늘 요리 중 '요리 완료'를 누른 비율 | 30% 이상 |
| 등록 소요 시간 | 재료 1개 등록에 걸린 중앙값 | 10초 이하 |

## 2. 핵심 기능 정의

기능은 일곱 묶음이고, MVP는 F1\~F4와 F5의 소셜 로그인까지 포함한다.

| ID | 기능 | 설명 | 우선순위 |
| --- | --- | --- | --- |
| F1 | 재료 등록·유통기한 자동 지정 | 이름 자동완성 → 재료 사전에서 카테고리·기본 보관 방식·단위 추천. 보관 방식(냉장/냉동/실온)을 바꾸면 기한 재계산. 날짜 직접 수정 가능. 별칭 인식(삼겹살→돼지고기) | MVP |
| F1-2 | 빠른 등록 | 최근 산 재료 원탭 재등록, 여러 개 한 번에 등록("양파 3, 두부 1, 계란 10") | MVP |
| F1-3 | 영수증·사진 등록 | 영수증 OCR 또는 장바구니 사진에서 재료 목록 추출 후 확인 | 2차 |
| F2 | 인터랙티브 냉장고 | 냉장고 문 열기/닫기, 칸별 재료 배치, 재료 탭 → 수량 조절·이동·삭제, 드래그로 칸 이동. 상세는 3장 | MVP |
| F3 | 다일 식단 플랜 | 유통기한이 급한 재료를 우선 소비하도록 3/5/7일 또는 "버틸 수 있는 만큼" 식단 생성. "N일 동안 M끼 가능" 요약, 버려질 위험 재료 경고 | MVP |
| F3-2 | 요리 완료 처리 | 요리를 하면 쓴 재료 수량이 자동 차감되고, 플랜이 다시 계산됨 | MVP |
| F3-3 | 레시피 상세 | 재료(보유/부족 표시), 단계별 조리법, 조리 시간, 인분 조절 | MVP |
| F4 | 최소 장보기 추천 | 1\~2가지만 사면 가능한 요리, "딱 하나만 산다면" 순위, 버릴 재료를 살리는 요리 우선. 장보기 목록 저장 | MVP |
| F4-2 | AI 맞춤 추천 | 기본 레시피 DB 밖의 요리를 LLM으로 생성, 취향·알레르기·조리도구 반영 | 2차 |
| F5 | 로그인·계정 | 카카오/구글/네이버 소셜 로그인, 내 냉장고 데이터 클라우드 저장 | MVP |
| F5-2 | 냉장고 공유 | 가족·룸메이트 초대, 한 냉장고를 여러 명이 편집 | 2차 |
| F6 | 알림 | 매일 아침 "오늘 먹어야 할 재료" 웹 푸시, 기한 D-1 알림 | 2차 |
| F7 | 통계 | 이번 달 다 쓴 재료·버린 재료, 아낀 금액 추정 | 3차 |

## 3. 인터랙티브 냉장고 UX

홈 화면은 목록이 아니라 냉장고 한 대다. 닫힌 문에는 급한 재료 수가 붙고, 문을 열면 칸마다 재료가 실제 물건처럼 놓여 있으며, 재료를 누르면 그 자리에서 수량을 바꾼다.

### 3.1 냉장고 구조

- **본체 2도어**: 위쪽 냉장실, 아래쪽 냉동실. 실온 재료는 냉장고 옆 '팬트리 선반'으로 따로 보여 준다.
- **냉장실 칸**: 선반 3단(위·중간·아래), 채소칸 서랍, 문 선반(소스·음료·계란). 칸은 재료 카테고리에 따라 자동 배치되고 사용자가 드래그로 옮길 수 있다.
- **냉동실 칸**: 서랍 2단. 서랍을 당기면 위에서 내려다보는 시점으로 바뀐다.
- **칸별 기본 배치 규칙**: 채소·과일 → 채소칸, 육류·해산물 → 아래 선반, 계란·유제품 → 문 선반·위 선반, 반찬·김치·가공품 → 중간 선반.

### 3.2 상태별 인터랙션

| 상태 | 화면 | 사용자 동작 | 애니메이션 |
| --- | --- | --- | --- |
| 닫힘 | 정면 냉장고, 문에 자석 배지("오늘까지 2", "3일 안에 4") | 문 탭 | 문이 경첩 쪽을 축으로 약 110° 회전하며 열림, 내부 조명이 켜지듯 밝아짐 (0.5초) |
| 열림 | 칸별로 재료 아이콘이 놓여 있음 | 재료 탭 / 칸 탭 / 바깥 탭 | 재료가 살짝 튀어 오르며 선택 표시, 바깥 탭 시 문 닫힘 |
| 칸 확대 | 선택한 칸이 화면을 채우고 재료가 크게 보임 | 핀치·뒤로가기 | 카메라가 칸으로 줌인 (shared layout) |
| 재료 시트 | 하단 시트에 이름, D-day, 수량 스테퍼, 보관 방식, 메모 | − / + 탭, 길게 눌러 연속 조절, 보관 방식 변경 | 수량이 줄면 아이콘 개수·채움 정도가 줄어듦 |
| 드래그 | 재료를 다른 칸이나 냉동실로 끌기 | 길게 누른 뒤 드래그 | 놓을 수 있는 칸이 하이라이트, 냉동실에 놓으면 새 기한 토스트 |
| 다 씀/버림 | 시트의 버튼 | 탭 | 다 씀: 재료가 접시로 날아감 · 버림: 휴지통으로 떨어짐 |

### 3.3 재료 오브젝트 표현

- **아이콘**: 재료별 일러스트 아이콘(양파, 계란, 두부 팩…). 사전에 없는 재료는 카테고리 아이콘 + 이름 라벨.
- **수량 표현**: 셀 수 있는 재료(계란 8개)는 개수만큼 쌓아 보여 주되 최대 6개까지, 넘으면 "×8" 뱃지. 무게·부피(돼지고기 600g, 우유 500ml)는 용기 채움 정도로 표현.
- **신선도 표현**: D-4 이상은 평소 모습, D-3\~2는 노란 테두리, D-1·D-day는 빨간 테두리와 미세한 흔들림, 지난 재료는 회색 처리 + 파리 아이콘. 색만으로 구분하지 않도록 D-day 텍스트를 항상 함께 표시.
- **냉동 재료**: 아이콘에 서리 오버레이.

### 3.4 플랜·레시피 연결

- 식단 플랜에서 요리를 누르면 냉장고 문이 열리며 그 요리에 쓰이는 재료만 밝게, 나머지는 어둡게 표시한다.
- '요리 완료'를 누르면 쓰인 재료가 칸에서 빠져나와 냄비로 모이는 애니메이션 후 수량이 차감된다.
- 부족한 재료는 냉장고 바깥에 점선 실루엣으로 표시하고, 누르면 장보기 목록에 추가된다.

### 3.5 접근성과 성능 기준

- `prefers-reduced-motion`이면 회전·줌 대신 페이드로 바꾼다.
- 냉장고 화면과 똑같은 정보를 담은 '목록 보기' 토글을 항상 제공한다(스크린리더·빠른 편집용).
- 저사양 모바일에서도 60fps를 유지하도록 3D 엔진 대신 CSS 3D transform + 2D 일러스트로 구현한다. 재료 200개까지 끊김 없이 동작하는 것을 기준으로 한다.

## 4. 화면 구성과 사용자 플로우

화면은 하단 탭 4개(냉장고 · 식단 · 장보기 · 마이)와 그 위에 뜨는 시트·모달로 구성한다. 첫 방문자는 로그인 없이 냉장고를 체험하고, 저장하려는 순간 로그인으로 이어진다.

요리를 마치거나 장을 봐 온 뒤에는 항상 냉장고 홈으로 돌아와 바뀐 재고를 확인하고, 플랜은 그 재고로 다시 계산된다.

| 화면 | 주요 요소 | 진입 |
| --- | --- | --- |
| 랜딩 | 문이 열리는 냉장고 데모, "로그인 없이 시작" / 소셜 로그인 버튼 | 최초 접속 |
| 온보딩 | 가구 인원, 하루 요리 끼니, 못 먹는 재료, 가진 조리도구(전자레인지·에어프라이어·오븐) 선택, 자주 사는 재료 빠른 등록 | 첫 로그인 |
| 냉장고 홈 | 인터랙티브 냉장고, 상단 "오늘의 한 끼" 카드, 재료 추가 FAB | 탭 1 |
| 재료 추가 시트 | 이름 자동완성, 보관 방식 세그먼트, 수량·단위, 자동 계산된 기한(수정 가능), 여러 개 연속 등록 | FAB, 칸 길게 누르기 |
| 재료 상세 시트 | D-day, 수량 스테퍼, 보관 방식 변경, 다 씀/버림, 이 재료로 만들 수 있는 요리 | 재료 탭 |
| 식단 플랜 | 기간·끼니 선택, "N일 · M끼 가능" 요약, 날짜별 카드, 버려질 위험 재료 배너 | 탭 2 |
| 레시피 상세 | 재료(보유/부족), 단계, 타이머, 인분 조절, 요리 완료 버튼 | 플랜·추천 카드 |
| 장보기 | "딱 하나만 산다면" 순위, 조금만 사면 되는 요리, 내 장보기 목록(체크 후 '냉장고에 넣기') | 탭 3 |
| 마이 | 프로필, 식습관 설정, 알림 설정, 통계, 냉장고 공유(2차), 로그아웃·탈퇴 | 탭 4 |

### 4.1 모바일 퍼스트 원칙

모든 화면은 세로 360\~430px 폰을 기준으로 먼저 설계하고, 태블릿·데스크톱은 그 화면을 넓혀 쓰는 방식으로 확장한다. 냉장고 앞에서 한 손으로 폰을 들고 쓰는 상황이 기본 시나리오다.

- **한 손 조작**: 하단 탭바, 오른쪽 아래 재료 추가 버튼, 바텀 시트 중심. 자주 누르는 버튼은 화면 아래 절반(엄지 영역)에 둔다.
- **터치 기준**: 터치 영역 최소 44×44px, 수량 스테퍼는 길게 누르면 연속 증감, 시트는 아래로 스와이프해 닫기.
- **냉장고 화면**: 세로 화면에 2도어 냉장고를 꽉 차게 그리고, 칸은 탭으로 확대한다. 드래그는 길게 누른 뒤 시작해 스크롤과 충돌하지 않게 한다.
- **기기 대응**: 노치·홈 인디케이터 영역(safe-area) 확보, 키보드가 올라와도 등록 버튼이 가려지지 않게 처리, 다크 모드 지원.
- **데스크톱 확장**: 1024px 이상에서는 왼쪽에 냉장고, 오른쪽에 식단 플랜을 나란히 보여 주는 2단 레이아웃.
- **성능 목표**: 중저가 안드로이드 4G 환경에서 첫 화면 표시(LCP) 2.5초 이하, Lighthouse 모바일 성능 90점 이상.

### 4.2 PWA 설치와 오프라인

PWA 기본 설정(매니페스트, 서비스 워커)은 1단계 코어 개발 때 넣고, 설치 안내와 오프라인 동작은 3단계 베타 전에 다듬는다.

| 항목 | 내용 |
| --- | --- |
| 매니페스트 | 이름 '냉털 레시피', 짧은 이름 '냉털', `display: standalone`, 시작 경로 `/fridge`, 테마 색, 아이콘 192·512px + maskable 아이콘, iOS용 apple-touch-icon과 스플래시 |
| 서비스 워커 | Next.js App Router용 PWA 라이브러리(Serwist 등)로 생성. 앱 셸·폰트·재료 아이콘은 미리 캐시, 재료 사전·레시피는 받은 뒤 캐시 |
| HTTPS | Vercel 기본 제공 |
| 설치 안내 (안드로이드·크롬) | `beforeinstallprompt` 이벤트를 받아 두었다가, 재료를 3개 이상 등록했거나 두 번째 방문일 때 "앱으로 설치하기" 배너를 띄운다. 닫으면 7일 동안 다시 띄우지 않는다 |
| 설치 안내 (iOS 사파리) | 자동 설치 창이 없으므로 "공유 버튼 → 홈 화면에 추가" 순서를 그림으로 보여 주는 안내 시트를 같은 조건에서 띄운다 |
| 오프라인 | MVP: 마지막으로 불러온 냉장고·플랜·레시피를 오프라인에서도 볼 수 있음. 2차: 오프라인에서 한 수정(수량 변경 등)을 기기에 쌓아 두었다가 온라인이 되면 동기화 |
| 푸시 알림 (2차) | iOS는 홈 화면에 설치한 웹앱에서만 웹 푸시를 받을 수 있으므로, 알림 켜기 버튼을 설치 안내와 연결한다 |
| 앱스토어 (3차 검토) | 필요하면 PWA를 그대로 감싸 Play 스토어에 등록하는 방식(TWA)을 검토한다. 스토어 등록비가 들기 때문에 사용자 반응을 본 뒤 결정한다 |

## 5. 추천 알고리즘

추천은 규칙 기반 플래너가 기본이고, LLM은 레시피 DB 밖의 요리를 보충하는 역할만 맡는다. 규칙 기반이어야 결과가 빠르고, 같은 재료면 같은 플랜이 나오며, 비용이 들지 않는다.

### 5.1 입력 데이터

- **재료 사전**: 재료별 카테고리, 보관 방식별 권장 일수(냉장/냉동/실온, 0이면 비권장), 기본 단위, 요리 1회 평균 사용량, 별칭.
- **레시피 DB**: 필수 재료("돼지고기 또는 참치캔"처럼 대체 가능 그룹 포함), 선택 재료, 레시피별 사용량, 조리 시간, 난이도, 필요한 조리도구.
- **기본 양념**: 간장·소금·고추장 등은 있다고 가정하고, 사용자가 마이 화면에서 끌 수 있다.
- **사용자 설정**: 하루 요리 끼니, 못 먹는 재료, 가진 조리도구.

### 5.2 다일 식단 플랜 (그리디 + 재계산)

1. 오늘부터 D일까지 하루씩 진행한다. 그날 이전에 기한이 지난 재료는 '버려짐'으로 분리한다.
2. 남은 재료로 만들 수 있는 레시피 후보를 모두 찾는다. 필수 재료 그룹마다 기한이 가장 급한 재료를 고른다.
3. 후보마다 긴급도 점수를 매기고 가장 높은 요리를 그 끼니에 배정한다. 같은 요리는 4일 안에 반복하지 않는다.
4. 배정된 요리의 사용량만큼 재료 수량을 차감하고, 끼니 수만큼 반복한다.
5. 기간을 다 돌거나 만들 요리가 없으면 멈추고, "N일 동안 M끼 가능"과 버려질 재료 목록을 낸다.

긴급도 점수는 쓰는 재료마다 남은 일수가 적을수록 크게 준다. d는 계획 중인 날짜, dl은 재료의 남은 일수, w는 필수 재료 1.3·선택 재료 1.0이다.

```latex
\text{score}(r, d) = \sum_{i \in r} w_i \left( \frac{10}{\max(dl_i - d,\, 0) + 1} + 0.4 \right)
```

- 2차 고도화: 그리디는 "오늘 최선"이 "전체 최선"이 아닐 수 있다. 재료 30개·7일 수준이면 빔 서치(폭 20)나 정수계획법으로 버려지는 재료 수를 최소화하는 방식으로 바꿀 수 있다.
- 재료가 등록·수정·요리 완료될 때마다 플랜을 다시 계산한다. 플래너는 TypeScript 순수 함수라 브라우저에서 수십 ms 안에 계산되고, 서버 비용이 들지 않는다.

### 5.3 최소 장보기 추천

1. 필수 재료 그룹 중 1\~2개만 부족한 레시피를 찾는다(보유 재료를 하나 이상 쓰는 경우만).
2. 부족 개수가 적은 순, 같으면 긴급도 점수가 높은 순으로 정렬한다. 플랜에서 '버려질 재료'를 쓰는 레시피에는 가산점을 준다.
3. 부족 재료가 하나인 레시피를 재료별로 묶어 "딱 하나만 산다면" 순위를 만든다. 기준은 살리는 위험 재료 수 → 새로 가능해지는 요리 수 → 점수 합.
4. 사용자가 장보기 목록에 담은 재료는 '산 것으로 가정'하고 플랜을 미리 보여 주는 시뮬레이션을 제공한다.

### 5.4 AI 보조 추천 (2차)

- 재료 목록, 남은 일수, 설정, 규칙 플랜 결과를 LLM에 보내고 JSON(날짜별 요리·사용 재료·추가 구매·조리법)으로 받는다.
- 응답의 재료명은 재료 사전과 다시 대조해 없는 재료를 지어내지 않았는지 검증한 뒤 보여 준다.
- 사용자당 하루 호출 횟수를 제한해 비용을 관리한다.

### 5.5 데이터 출처 (확인 필요)

- 레시피: 식품안전나라의 조리식품 레시피 공공 API를 1차 후보로 검토하고, 부족한 가정식은 직접 정리한다. 라이선스와 데이터 품질은 착수 전에 확인한다.
- 보관 기한: 공공기관 식품 보관 가이드를 바탕으로 사전을 만들고, 출처를 재료별로 기록한다. 기한은 '권장'임을 화면에 명시한다.

## 6. 기술 아키텍처와 스택

비용 0원, 관리할 서버 0대를 목표로 한다. Next.js 앱 하나를 Vercel에 올리고 DB·로그인은 Supabase에 맡긴다. 별도 백엔드가 없으니 배포, 인증 연동, 비용 관리가 모두 단순해진다. 무료 플랜 조건은 자주 바뀌므로 착수할 때 각 요금 페이지에서 다시 확인한다.

&#91;embedded content: 시스템 구성 · 별도 백엔드 없음, 점선은 2차\]

| 영역 | 선택 | 비용 |
| --- | --- | --- |
| 앱 (화면 + 서버) | Next.js (App Router) + TypeScript, 필요할 때만 Route Handler | 무료 |
| 호스팅 | Vercel Hobby, PWA로 홈 화면 설치 | 무료 (비상업 용도 조건, 수익화하면 유료 플랜 전환) |
| DB · 로그인 | Supabase 무료 플랜: Postgres + Auth(카카오·구글 OAuth) + RLS | 무료 (용량 제한, 오래 안 쓰면 프로젝트 일시정지) |
| 추천 로직 | 플래너·장보기 추천을 TypeScript 순수 함수로 작성해 브라우저에서 계산 | 무료 (서버 연산 없음) |
| 애니메이션 | Motion(Framer Motion) + CSS 3D transform, SVG 재료 아이콘 | 무료 |
| 스타일 | Tailwind CSS | 무료 |
| 알림 (2차) | Web Push(VAPID) + GitHub Actions 예약 실행 | 무료 |
| AI (2차) | 무료 할당량이 있는 LLM API, 사용자당 하루 호출 제한 | 무료 할당 안에서 |
| 에러 추적 | Sentry 무료 플랜 | 무료 |
| 도메인 | 처음엔 vercel.app 주소, 공개 베타 때 구입 검토 | 선택 (연 1\~2만 원) |

**인증 흐름**

1. 카카오·구글 로그인 버튼 → Supabase Auth가 OAuth를 처리하고 `auth.users`에 저장한다.
2. 첫 로그인 시 DB 트리거가 `profiles`, 기본 냉장고, 칸 구조를 만든다.
3. 브라우저에서 supabase-js로 DB를 바로 읽고 쓴다. RLS 정책으로 내 냉장고 데이터만 접근할 수 있다.
4. 비로그인 체험 데이터는 브라우저 저장소에 두었다가, 로그인 직후 한 번에 업로드한다.

## 7. 데이터 모델과 API

냉장고를 사용자와 분리해 두면 2차 '냉장고 공유'를 테이블 하나(`fridge_members`)로 붙일 수 있다. 재료 사전과 레시피는 모든 사용자가 같이 쓰는 마스터 데이터다.

### 7.1 테이블

| 테이블 | 주요 컬럼 | 비고 |
| --- | --- | --- |
| users | id, email, nickname, avatar\_url, created\_at | Supabase auth.users와 1:1 프로필 |
| accounts / sessions | provider, provider\_account\_id, user\_id | Supabase Auth가 관리, 직접 만들지 않음 |
| user\_preferences | user\_id, meals\_per\_day, excluded\_ingredient\_ids\[\], tools\[\], pantry\_overrides JSONB, notify\_time | 온보딩에서 입력 |
| fridges | id, name, owner\_id, created\_at | 사용자당 기본 1개 |
| fridge\_members | fridge\_id, user\_id, role(owner/editor) | 2차 공유 기능 |
| compartments | id, fridge\_id, zone(fridge/freezer/room), kind(shelf/drawer/door), position | 칸 구조, 기본값 자동 생성 |
| ingredients | id, name, category, aliases\[\], default\_unit, use\_per\_recipe, shelf\_fridge\_days, shelf\_freezer\_days, shelf\_room\_days, default\_storage, icon\_key, source | 재료 사전(마스터) |
| fridge\_items | id, fridge\_id, ingredient\_id(null 허용), custom\_name, compartment\_id, storage, quantity, unit, purchased\_at, expires\_at, expires\_manual, memo, created\_at, updated\_at | 사용자가 넣은 재료 |
| item\_events | id, item\_id, fridge\_id, type(added/used/cooked/discarded/moved/edited), quantity\_delta, recipe\_id, created\_at | 통계·되돌리기용 이력 |
| recipes | id, name, minutes, difficulty, servings, tools\[\], steps JSONB, image\_key, source | 레시피(마스터) |
| recipe\_ingredients | recipe\_id, group\_no, ingredient\_id, required, amount, unit | 같은 group\_no = 대체 가능 |
| shopping\_items | id, fridge\_id, ingredient\_id, name, quantity, checked, from\_recipe\_id | 장보기 목록 |
| cook\_logs | id, fridge\_id, recipe\_id, cooked\_at, servings | 요리 완료 기록 |

### 7.2 데이터 접근 (별도 API 서버 없음)

| 작업 | 방식 |
| --- | --- |
| 재료 사전 검색 | 앱 시작 시 `ingredients`를 한 번 받아 캐시, 이름·별칭 자동완성은 브라우저에서 |
| 기한 계산 | 클라이언트 함수 `calcExpiry(ingredient, storage, purchasedAt)` |
| 재료 등록·수정·다 씀·버림 | supabase-js로 `fridge_items` insert/update + `item_events` 기록, 권한은 RLS가 확인 |
| 식단 플랜 | `buildPlan(items, recipes, days, meals)` 브라우저 계산 |
| 장보기 추천 | `suggestShopping(items, recipes, riskItems)` 브라우저 계산 |
| 요리 완료 | Postgres 함수(RPC) `cook_recipe` 하나로 재고 차감과 `cook_logs` 기록을 한 트랜잭션에 처리 |
| 장보기 목록 | `shopping_items` 조회·추가·체크, 체크한 항목은 `fridge_items`로 옮김 |
| 설정 | `user_preferences` 조회·수정 |
| AI 추천 (2차) | Next.js Route Handler 한 곳에서만 LLM 호출 (API 키 보호) |

## 8. MVP 범위와 로드맵

MVP는 착수 후 11주차 공개 베타를 목표로 한다. 퇴근 후 사이드 프로젝트로 주 10\~12시간을 쓴다고 가정한 일정이며, 시간이 더 나면 4단계를 앞당긴다.

**MVP에 넣는 것**

- [ ] 소셜 로그인(카카오·구글), 비로그인 체험 → 로그인 시 데이터 이전
- [ ] 재료 사전 150종 + 별칭, 보관 방식별 기한 자동 계산
- [ ] 재료 등록·수정·다 씀·버림, 목록 보기
- [ ] 인터랙티브 냉장고: 문 열기, 칸 배치, 재료 시트에서 수량 조절, 드래그로 칸·냉동실 이동
- [ ] 레시피 100개, 다일 식단 플랜, 요리 완료 시 자동 차감
- [ ] 최소 장보기 추천과 장보기 목록

**MVP에서 빼는 것**: 냉장고 공유, 푸시 알림, AI 추천, 영수증 OCR, 통계.

&#91;embedded content: 로드맵 · 5단계, 단계 사이 완료 기준 4개\]

단계 사이 마름모는 완료 기준이다. 특히 코어 기능을 목록 화면으로 먼저 완성해 두면, 냉장고 연출이 늦어져도 서비스는 쓸 수 있다.

## 9. 리스크와 결정이 필요한 사항

가장 큰 리스크는 "재료 등록이 귀찮아서 그만 쓰는 것"이다. 그래서 MVP에서도 빠른 등록과 자동 기한 계산을 가장 먼저 다듬는다.

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 등록 피로로 이탈 | 냉장고 데이터가 실제와 달라져 추천이 무의미해짐 | 자동완성·연속 등록·최근 재료 원탭, 2차에 영수증 OCR |
| 유통기한 정확도 | 잘못된 기한으로 식품 안전 문제 | 기한은 '권장'으로 표기, 사용자 수정 허용, 재료별 출처 기록 |
| 레시피 데이터 양·품질 | 추천이 단조로움 | 공공 API + 직접 큐레이션, 2차 AI 보충 |
| 수량 단위 불일치 | 사용량 차감이 부정확함 | 재료별 기본 단위 고정 추천, 단위가 다르면 '한 번에 다 씀'으로 처리하고 수정 유도 |
| 애니메이션 성능 | 저사양 기기에서 끊김 | CSS 3D 중심, 화면 밖 재료는 렌더 생략, 목록 보기 제공 |
| AI 비용 | 사용자 증가 시 비용 급증 | 규칙 플래너 우선, 일일 호출 제한, 결과 캐시 |

**결정이 필요한 사항**

- [ ] 냉장고 비주얼 스타일: 플랫 2D 일러스트 vs 아이소메트릭 2.5D
- [ ] 첫 출시 로그인 제공자: 카카오·구글만 vs 네이버 포함
- [ ] 레시피 출처: 공공 API 사용 범위와 라이선스 확인
- [ ] 수익 모델 검토 여부: 무료 유지 vs 장보기 제휴(마트 연동) 등
- [ ] 도메인과 서비스 이름 '냉털 레시피' 상표 검색
