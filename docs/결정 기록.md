## D1. 냉장고 비주얼 스타일: 장난감 같은 3D

처음에는 플랫 2D 일러스트로 정했지만(2026-10-14), 2026-10-29 사용자 요청으로 앱 전체를 3D로 바꿨다.
사용자와 합의한 범위: 장난감 같은 3D(사실적인 3D 모델 파일은 쓰지 않음), 2D 대체 화면 없이 3D만, 인트로·냉장고·레시피를 한 번에.

- three.js + React Three Fiber. 냉장고 화면에서만 따로 내려받는다 (첫 화면 무게를 늘리지 않게).
- 재료 268종의 3D 모델은 2D 일러스트와 같은 설계도(`src/data/ingredient-art/specs.ts`)로 코드에서 만든다 (`src/three/models.ts`). 재료 하나를 한 덩어리로 구워 그리기 호출 1~3번.
- 보이는 것은 3D, 누르는 것은 DOM: 칸 영역·재료 이름표·문/서랍 버튼은 3D 위치를 따라다니는 진짜 버튼이다 (`src/components/fridge3d/overlay.ts`). 화면 읽기·키보드·드래그·E2E가 그대로 동작한다.
- 성능: 필요할 때만 그리기(가만히 있거나 스크롤할 때는 다시 그리지 않음), 그리기 해상도 1.5배 제한, 재료 200개에 그리기 호출 약 340번. `npm run test:perf`가 지킨다.
- 첫 방문 인트로(냉장고로 걸어가 문 열기)는 탭마다 한 번, 건너뛸 수 있다. 움직임 줄이기 설정이면 인트로를 빼고 문·서랍·카메라를 바로 옮긴다.
- 기획서 3.5절의 "3D 엔진 없이"라는 성능 기준은 이 결정으로 바뀐다. 실제 저사양 폰에서의 3D 애니메이션 속도는 실기기 확인이 필요하다.

## D2. 로그인 제공자: 카카오·구글만

- Supabase Auth가 카카오·구글을 기본 제공자로 지원한다. 네이버는 기본 제공자에 없어서 별도 OIDC 연동이나 커스텀 처리가 필요하다.
- 타깃인 20~30대 1인 가구는 카카오 로그인만으로 대부분 커버된다.
- 네이버는 베타 피드백에서 요청이 많으면 4단계에서 추가한다.

## D3. 레시피 출처: 직접 작성 우선, 공공 API는 보조

- 식품안전나라 "조리식품의 레시피 DB"(COOKRCP01) API는 메뉴명, 재료정보, 조리 순서 20단계, 단계별 이미지, 영양 정보 등 55개 필드를 제공한다. 자세한 조건은 [데이터 출처 확인](./데이터%20출처%20확인.md)에 적었다.
- 그러나 API 안내 페이지에 공공누리 유형이 표시되어 있지 않다. 재배포 조건을 확인하기 전에는 레시피 본문·이미지를 서비스에 그대로 싣지 않는다.
- 재료정보 필드가 자유 텍스트("돼지고기 200g, 양파 1/2개…")라 재료 사전과 연결하려면 어차피 수동 정제가 필요하다.
- 따라서 MVP 레시피 100개는 재료 사전 ID·사용량·대체 그룹을 직접 정의해 작성하고, API는 조리 단계 참고와 이후 레시피 확장에 쓴다.

## D4. 수익 모델: 무료 유지

- Vercel Hobby 플랜은 개인·비상업 용도만 허용한다. 광고·결제·제휴 수익이 생기면 Pro 플랜(유료)으로 바꿔야 한다.
- 비용 0원 목표와 맞물려 베타 기간에는 수익화를 하지 않는다.
- 장보기 제휴 등은 지표가 쌓인 뒤 5단계에서 다시 본다.

## D5. 도메인·상표: 미결

- '냉털 레시피' 상표 검색은 [KIPRIS](https://www.kipris.or.kr/)에서 직접 해야 한다. 자동화하지 않는다.
- 도메인은 공개 베타까지 vercel.app 주소를 쓰고, 베타 반응을 본 뒤 구입을 검토한다.

## D6. 재료 사전·레시피: 앱 번들에 포함

기획서 7.2절은 "앱 시작 시 `ingredients`를 한 번 받아 캐시"라고 했지만, 번들에 포함하는 쪽으로 바꿨다.

- 비로그인 체험과 오프라인에서도 자동완성·기한 계산·플래너가 바로 동작한다. 첫 화면에 네트워크 왕복이 없다.
- 데이터 크기가 작다 (재료 268종, 레시피 232개). gzip 기준 수십 KB 수준이다.
- 원본은 `src/data/*.ts` 하나이고, DB 시드는 `npm run gen:seed`로 같은 원본에서 만든다. 테스트가 시드 파일이 최신인지 확인하므로 둘이 어긋나지 않는다.
- DB의 마스터 테이블은 외래 키(재료·레시피 id 검증)와 서버 쪽 RPC(요리 완료, 체험 데이터 이전)를 위해 유지한다.
- 레시피가 수천 개로 늘거나 배포 없이 바꿔야 할 일이 생기면 DB에서 받는 방식으로 다시 검토한다.

## D7. 서비스 워커: 직접 작성

기획서 4.2절은 "Serwist 등 PWA 라이브러리로 생성"이라고 했지만 직접 작성했다.

- 이 프로젝트는 Turbopack으로 빌드한다. Serwist의 Next.js 연동은 webpack 빌드를 전제로 해 왔고, Turbopack 지원 여부를 확인하지 못했다.
- 필요한 동작이 단순하다: 앱 셸·아이콘 미리 캐시, 빌드 정적 파일 캐시 우선, 화면은 네트워크 우선 후 캐시. 100줄 안쪽이다.
- 의존성이 없어 Next.js 업그레이드에 영향을 받지 않는다.
- 오프라인에서 새로 고침해도 화면이 뜨는지 E2E(`e2e/pwa.spec.ts`)로 확인한다.
- 2차의 오프라인 쓰기 동기화나 웹 푸시가 복잡해지면 그때 라이브러리를 다시 검토한다.

## D8. 재료 아이콘: 코드로 그린 입체 일러스트

처음에는 이모지로 임시 대체했지만, 같은 날 사용자 요청으로 직접 그린 일러스트로 바꿨다.

- 재료 268종 모두에 그림이 있다. `src/data/ingredient-art/kit.ts`의 부품(둥근 과일, 길쭉한 채소, 잎채소, 버섯, 고기, 생선, 조개, 병, 팩, 통, 캔, 봉지 …)에 재료마다 색·모양·포장 라벨을 따로 정한다 (`specs.ts`).
- 입체감은 왼쪽 위에서 빛이 드는 그라데이션, 반들거리는 하이라이트, 바닥 그림자로 낸다. 기획서 3.5절 성능 기준 때문에 3D 엔진·실제 3D 모델은 쓰지 않는다 (사용자와 합의). blur 같은 SVG 필터도 저사양 폰에서 느려 쓰지 않는다.
- SVG 문자열을 재료마다 한 번만 data URL로 만들어 `<img>`로 쓴다. 재료 200개(겹쳐 쌓기 포함)에서도 CPU 4배 감속 기준 프레임 중앙값 16.7ms (`npm run test:perf`).
- 사전에 없는 재료는 분류 그림, 분류도 없으면 장바구니 봉지를 쓴다. 냄비·접시·휴지통·탭 아이콘 같은 화면 장식도 같은 스타일로 그렸다 (`ui.ts`).
- 포장 라벨(간장, 고추장 …) 글자는 기기 기본 한글 글꼴로 그려져 기기마다 조금 다르게 보인다.
- 디자이너가 일러스트를 따로 만들면 `ingredientArtUrl()` 한 곳만 바꾸면 된다. 사실적인 3D 모델을 쓰려면 모델 파일(glTF) 확보와 성능 기준 재검토가 먼저 필요하다.
